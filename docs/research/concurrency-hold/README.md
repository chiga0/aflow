# 多并发 / 任务编排 hold 决策分析

> 结论先行：**加阀门，不加调度器**。除 L1 外全部 hold；L1 也等真实痛点出现再做。
> 状态：hold（2026-08-04 与用户对齐）。

## 1. 背景

aflow-lite 控制面刻意保持单进程 + stdlib + SQLite。多 Agent 编排（多并发、
任务分配、worker 池）是长期目标，但用户直觉"会很复杂导致其他问题"，
本文件把复杂度摊开算账，并给出分级路线与触发条件。

## 2. 并发解决谁的痛点？

单用户场景下并发的价值只有两类：

- A. 多个后台长任务同时跑，等通知收结果
- B. 后台任务跑着的同时，交互式会话不被阻塞

关键洞察：

- **A 用"队列 + 推送"即可满足，不需要真并行**。任务排队执行、完成推锁屏，
  用户注意力本来串行，墙钟并行无感知收益。
- **B 只需要并发数 = 2**（1 交互 + 1 后台），不需要调度器。

## 3. 复杂度账单

| 维度 | 现状（单进程） | 多并发后 |
|---|---|---|
| 内存 | 1×pi ≈ 200MB 可控 | N×200MB + agent 内 npm/build 峰值 ≈800MB；1.6G VPS 上 2 并发即可能 OOM → 必须准入控制 |
| 进程生命周期 | spawn/reap 单路径 | 泄漏/僵尸/deploy drain/崩溃恢复 ×N |
| 状态一致性 | 内存 + SQLite，SSE 直连 | 多副本下 SSE 订阅与 turn 跨进程 → 需事件总线（Redis）→ stdlib/SQLite 资产作废 |
| 审批 | 单通道上下文清晰 | 多任务抢注意力 → 审批疲劳 → 误允许 → 安全事故 |
| 爆炸半径 | 跑飞只影响自己 | 无隔离时一个 fork 炸弹杀死全部 → 需 cgroup/docker |
| 成本 | 单流 | N 路并发燃烧 → 需预算闸 |
| 可调试性 | 单日志流 | 需 per-task tracing |

历史参照：旧 v1/v2（37k 行）即"编排/多租户/worker 调度先行，用户闭环后补"
的产物，README 自评"没有一个用户闭环真正跑通"。多并发是该路径入口。

## 4. 分级路线（每级需触发条件才升级）

- **L0 现状**：chat 单 turn + missions sequential。push + 消息队列已提供异步体验。
- **L1（~100 行，等真实排队痛点再做）**：全局信号量 MAX_CONCURRENT=2 +
  FIFO 队列 + 队列 UI 可见 + 排队/完成推送。覆盖 A+B。
- **L2（出现真实跑飞案例再做）**：per-task 隔离（docker --memory / cgroup）。
  只隔离，不编排。
- **L3（第二台机器/第二个人再用）**：worker 池 + 任务分发；此时必须
  PostgreSQL + 事件总线，等于重写控制面——届时重新评估是否值得。
- **永不做**：抢占调度、优先级队列、跨机迁移（团队产品需求，非本场景）。

## 5. 替代视角

把编排交给 agent 层：pi 支持子 agent / 工具调用，"拆分并行"作为模型行为存在，
控制面保持 dumb。复杂度留在可丢弃层，而非基础设施层。

## 6. 决策记录

- 2026-08-04：hold。不实现 L1+；等"排队等得不耐烦"的真实时刻。
- 复查触发条件：单周 ≥3 次"任务互相阻塞"抱怨；或出现第二个常驻用户。
